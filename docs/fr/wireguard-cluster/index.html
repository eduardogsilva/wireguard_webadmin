Cluster

Cluster WireGuard

Exécutez WireGuard sur plusieurs serveurs et gérez-les tous depuis un seul panneau.

Fonctionnement

Le serveur principal est l’endroit où vous gérez tout : instances, pairs, pare-feu, DNS et applications de l’App Gateway. Les nœuds workers exécutent un agent léger qui se connecte au serveur principal, reçoit la configuration et l’applique localement. Les workers n’ont ni panneau ni base de données propres : un nouveau nœud est prêt en quelques minutes.

1 Le worker se connecte

L'agent s'authentifie avec son jeton et appelle le serveur principal en HTTPS. Les workers n'établissent que des connexions sortantes.

2 Synchronisation

Les paramètres WireGuard, pare-feu, DNS et App Gateway sont envoyés en sections distinctes. Seul ce qui a changé est réappliqué.

3 État

Chaque worker remonte au serveur principal l'état de WireGuard, le trafic des pairs, les services et les certificats.

4 Une seule vue

La liste des pairs indique sur quel serveur chaque pair est connecté, dans tout le cluster.

Modes du cluster

Miroir
Tous les nœuds exécutent toutes les instances WireGuard avec les mêmes pairs. L'utilisateur choisit le serveur en téléchargeant la configuration ou en ouvrant une invitation VPN : le même pair peut donc se connecter via n'importe quel nœud. Utile pour la redondance et pour des serveurs situés dans différentes régions.
Distribué
Chaque instance WireGuard s'exécute sur un seul serveur, choisi dans les paramètres de l'instance (le serveur principal par défaut). Utile pour répartir les instances entre plusieurs sites ou garder chaque réseau à son propre emplacement.

Le serveur principal comme simple gestionnaire

En mode miroir, WireGuard peut être désactivé sur le serveur principal. Celui-ci arrête ses interfaces WireGuard, n’est plus proposé comme serveur aux pairs et ne publie que le panneau WireGuard WebAdmin, tandis que les workers continuent de servir tous les pairs.

Avant de le désactiver, assurez-vous de pouvoir accéder au panneau sans le VPN du serveur principal.

App Gateway sur les workers

Les workers installés avec l’App Gateway publient aussi vos applications Zero Trust. Chaque application choisit où elle est servie : sur le serveur principal, sur tous les workers ou sur des workers sélectionnés.

Les certificats sont émis par le serveur principal puis distribués aux workers : les applications publiées par les workers doivent donc utiliser la validation DNS ou des certificats auto-signés.

Ajouter un worker

01
Activer le cluster

Dans les paramètres du cluster du serveur principal, activez le cluster et choisissez le mode. Le cluster utilise le cache d'état de WireGuard, activé par défaut.

02
Créer le worker

Ajoutez un worker avec un nom et le nom d'hôte utilisé par les clients pour le joindre : il devient le point de terminaison des configurations de pairs téléchargées pour ce serveur. La page du worker affiche son jeton et les commandes d'installation.

03
Récupérer le fichier compose sur le serveur du worker
mkdir wireguard_webadmin_node && cd wireguard_webadmin_node
wget -O docker-compose.yml \
  https://raw.githubusercontent.com/eduardogsilva/wireguard_webadmin/main/cluster_node.yml
mkdir wireguard_webadmin_node && cd wireguard_webadmin_node
wget -O docker-compose.yml \
  https://raw.githubusercontent.com/eduardogsilva/wireguard_webadmin/main/cluster_node-gateway.yml
04
Créer le fichier .env
MASTER_SERVER_ADDRESS=https://vpn.example.com
TOKEN=jeton-affiche-sur-la-page-du-worker
TIMEZONE=Europe/Paris
05
Démarrer le worker
docker compose up -d

Prérequis réseau

  • Les workers doivent joindre le serveur principal en HTTPS. Si l’App Gateway protège le panneau du serveur principal, ajoutez une route pour /api/cluster/ avec une politique publique.
  • Publiez les ports WireGuard (51820-51839/udp) sur chaque worker et, avec l’App Gateway, les ports 80 et 443.

Mettre à jour un worker

Exécutez docker compose pull puis docker compose up -d. Pour passer de VPN uniquement à VPN et App Gateway, ou l’inverse, téléchargez l’autre fichier compose dans le même répertoire et exécutez docker compose up -d --remove-orphans. Les données du worker sont conservées.

Supervision et automatisation

La page du worker indique quand il a été vu pour la dernière fois, la version de son agent, l’état de synchronisation de chaque section, ses services et ses certificats.

  • Désactivez un worker et il arrête ses interfaces WireGuard jusqu’à sa réactivation.
  • Le verrouillage IP n’accepte le worker que depuis une adresse IP fixe.
  • L’API v2 permet à des outils externes d’activer et de désactiver les workers et le WireGuard du serveur principal. La clé d’API doit avoir l’autorisation de gestion du cluster.

Toujours une seule stack. Le cluster est facultatif : un serveur seul continue de fonctionner exactement comme avant, et des workers peuvent être ajoutés à tout moment.
